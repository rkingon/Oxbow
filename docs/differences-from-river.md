# Differences from River

Reference: River `main` at `1f19003`. Each entry gives what differs and why.

| Area | River | Oxbow | Why |
|---|---|---|---|
| Driver | Pluggable drivers (pgx, `database/sql`, SQLite) | Npgsql only, no driver abstraction | .NET has one Postgres driver. An abstraction would be surface with no second implementation behind it. |
| Migrations | `rivermigrate` runs DDL and tracks it in `river_migration` | Consumer applies the SQL from `OxbowSchema`, EF, or the CLI. `{p}migration` is only a version marker checked at startup | The consumer owns migrations and the runtime never runs DDL. |
| Schema history | Migrations 001–008 | Version 1 = River's state at 008, without `river_migration`, `river_notification` (SQLite outbox) or `river_client*` | Greenfield, so there's no history to replay. |
| Naming | Configurable schema; fixed `river_` prefix | Configurable schema; configurable prefix on every created object: tables, enum, functions, indexes, NOTIFY channels (default `public`, `oxbow_`) | Lets several apps, or test runs, share a database. |
| Reindexer | Leader runs `REINDEX` on job indexes | Not included | `REINDEX` needs ownership, and the runtime role has none. Consumers schedule it as the owner if needed. |
| Rescuer, unknown kind | Discards a stuck job when the leader has no worker for its kind | Retries it with the global retry policy, discarded only by attempts | The leader may legitimately not run that kind's queue (queues are the routing boundary), so the leader's worker set says nothing about whether the kind exists. |
| Job kind | `Kind()` method on the args struct | `[JobKind("…")]` attribute | A static abstract interface member would make `IJobArgs` unusable as a type argument (CS8920). |
| Unique fields | `river:"unique"` struct tag | `[UniqueKey]` property attribute, read via `JsonPropertyInfo.AttributeProvider` | Works with System.Text.Json source generation. |
| Worker control flow | `JobSnooze`/`JobCancel` sentinel errors | `JobSnoozeException`/`JobCancelException` | .NET reports failure with exceptions. |
| Worker-chosen retry delay | None. `JobSnooze` waits without spending an attempt or recording an error; `NextRetry` on the worker sees only the job | `JobRetryException(delay, message)` fails the attempt, records the error, and retries at exactly `now + delay`, ahead of `GetNextRetry` and `IRetryPolicy` | A `Retry-After` is known only while working, and it's still a failure that should count toward `MaxAttempts` and show in `errors`. |
| Cancellation context | `context.Context` cancel cause | One `CancellationToken`. The executor tracks which source (remote, timeout, shutdown) fired | Workers only need to honor the token. |
| Hooks | Separate hook interfaces (`InsertBegin`, `WorkBegin`, `WorkEnd`, …) alongside middleware | Insert and work middleware only | Middleware covers every hook point and is the ASP.NET Core shape .NET developers already know. |
| Job output | `river.RecordOutput`, stored in `metadata.output`, up to 32 MB | `job.SetOutput`, stored in `metadata.output`, up to 1 MiB (`JobRow.MaxOutputSize`) | The output rides in the job row and through the batched completion. Large results belong elsewhere, with a reference in the output. |
| Discard hook | None; hooks (`WorkEnd`) and `client.Subscribe` see failures as they happen | `IJobDiscardHandler`, called after a discard or cancellation is written, including the rescuer's and the scheduler's | Middleware only sees what the worker did, not the state written (a retry that became a cancellation) or discards that happen without a worker. |
| Event subscription | `client.Subscribe(kinds…)` channel | Not included; covered by `Meter`/`ActivitySource` and middleware | Conventional .NET observability instead of a bespoke event stream. |
| Workflows, plugins | River Pro, or recent OSS additions | Not included | Out of scope for parity v1. |
| Resumable jobs | `ResumableStep` and `ResumableStepCursor` ([`resumable.go`](https://github.com/riverqueue/river/blob/1f19003/resumable.go)): steps return only an error, and the last completed step's name (plus per-step cursors) is kept in the job's metadata, written with the attempt's outcome, or at once with `ResumableSetStepTx`. A retry skips steps in order until it passes that name | `job.StepAsync(name, run)` returns a value, and each step's result is recorded in `{p}job_step` as soon as it runs. A later execution returns recorded results by name, in any order. First result recorded wins; a known-superseded attempt can't run or replay a step | A step's result is what later steps need (an ID a vendor returned, a model's reply), so it has to be stored, not just the fact the step ran. Recording each step at once survives a crash or rescue mid-attempt, which a checkpoint written with the outcome doesn't. |
| Attempt lock | None; an attempt's own writes aren't fenced against its rescue | `job.LockAttemptAsync(transaction)`: `FOR SHARE` on the job row while the attempt is current, failing the transaction if it isn't | A rescued attempt that keeps running would otherwise commit writes alongside its replacement's. |
| Durable periodic jobs | River Pro: only jobs given an `ID` are durable. `river_periodic_job` stores each one's next run time, and definitions stay in code | Every periodic job is durable. Unnamed jobs get a name derived from kind and schedule. Jobs can also be stored whole (kind, args JSON, options, schedule) and created, replaced, paused and deleted through `IOxbowClient` | The failover fix shouldn't be opt-in. Runtime CRUD is the roadmap's "schedules at runtime". |
| Periodic schedule change | River Pro: changing a durable job's schedule has no effect until the stored next run passes; the docs advise a new ID | The leader stores its registered schedule and recomputes the next run when it differs | Changing the code should change the schedule. |
| Periodic `RunOnStart` | Runs on every client start or leader election, durable jobs included | Runs only when the job has no persisted state yet | With persisted state, a run on every leader change is the repeat that durability exists to prevent. |
| Periodic enqueue atomicity | Not documented for durable jobs | The run's insert and the `next_run_at` advance share a transaction guarded on the row as read | Two leaders across a failover can't both enqueue a run. |
| Periodic job metadata | `"periodic": true` | `"oxbow:periodic_job": "<name>"` | Says which schedule enqueued the job. |
| Batches | Not in River; River Pro has workflows (a DAG of dependent jobs) | `InsertBatchAsync` with `OnComplete`/`OnSuccess` callback jobs, modeled on Sidekiq batches | Fan-out/fan-in without a workflow engine. The batch and its jobs are inserted in one statement, so a batch is never seen before its jobs. |
| Bulk insert | `InsertMany` (unnest, returning rows) and `InsertManyFast` (COPY, count only) | Same split: `InsertManyAsync` (unnest, rows returned, unique jobs supported) and `InsertManyFastAsync` (binary COPY, count only, unique jobs rejected) | — (parity) |
| Bulk job operations | `JobDeleteMany`, with `UnsafeAll()` to match every job | `CancelManyAsync`, `RetryManyAsync`, `DeleteManyAsync` over a `JobFilter` (the base of `JobListQuery`, which they reject); `All = true` to match every job. Batched by ID, counts returned | A match can be millions of rows: one statement would lock them all, and returning them all is unbounded. |
| EF insert | — | Throws without `Database.CurrentTransaction` | Otherwise the job commits ahead of `SaveChanges`. |
| Contracts package | One `river` package; inserting on a transaction takes a driver transaction (`InsertTx`) | `Oxbow.Abstractions`: args, workers and `IOxbowClient` without Npgsql. An optional `IOxbowTransactionAccessor` makes the scoped client insert in the ambient transaction, and `RequireAmbientTransaction` rejects inserts outside one | .NET apps commonly keep domain and application projects free of infrastructure packages. Without an ambient transaction those projects couldn't enqueue transactionally. |
| Tracing | None built in | `oxbow.insert`/`oxbow.work` spans; `traceparent` stored in metadata and linked | OpenTelemetry is the .NET convention. A link, not a parent, because work can run hours later. |
| Heartbeat and progress | None; the rescuer judges a job by `attempted_at` and its timeout | `HeartbeatAsync` and `ReportProgressAsync` on the job, stored in metadata; the rescuer uses the later of `attempted_at` and the heartbeat, and an attempt that has heartbeated is rescued once `RescueStuckJobsAfter` passes without a heartbeat, regardless of its timeout (even none) | Long jobs, jobs with no timeout, and kinds the leader doesn't run can't otherwise be told apart from dead ones. |
| Rescue metadata key | `river:rescue_count` | `oxbow:rescue_count` | Namespace. |
| Concurrency limits | River Pro: `GlobalLimit`/`LocalLimit` per queue, partitioned at fetch time by `ByArgs` fields and `ByKind`; without partitioning the limit covers the whole queue | `ConcurrencyLimit { Global, Local }` per queue, applied per `partition_key`, which is stored at insert (`InsertOptions.PartitionKey`, args defaults, `[PartitionKey]` properties, or insert middleware). Jobs without a key are unlimited, and kind isn't part of the key unless you put it there | A stored key is indexable, so counting running jobs per key is cheap, and the key can come from anything known at insert, not only args. Per-kind limits are a key prefix or a queue of their own. |
| Rate limiting | None in River, and River Pro documents concurrency limits but no rate limiter | `QueueOptions.RateLimit` and `PartitionRateLimit` (per key): GCRA on database time, one timestamp per limiter, enforced at fetch under the queue lock, with an optional burst. Modeled on Sidekiq Enterprise's and BullMQ's rate limiters | Workarounds (one worker on one node, a limiter in middleware that waits and burns the timeout, snoozing) don't hold across nodes or spend attempts. |
| Pausing an unknown queue | `QueuePause` returns not-found | Creates the queue row already paused | Lets a deploy pause a queue before any node has run it. |
| Sequence key | `SequenceOpts()` with `ByArgs`, `ByQueue`, `ExcludeKind` | `[SequenceKey]` properties (kind plus their values), or an explicit `InsertOptions.SequenceKey` string used verbatim | A plain string covers by-queue, cross-kind and custom keys without more options, and the attribute mirrors `[UniqueKey]`. |
| Halting on cancel | Any cancelled or discarded job halts the sequence unless `ContinueOnCancelled`/`ContinueOnDiscarded` | Only a job that ran (was ever fetched, even if it then snoozed) halts; cancelling one that never started takes it out of the line | A job that never ran left no partial effects, so there's nothing to stop for. Flags are `SequenceContinueOn.Cancelled`/`Discarded`. |
| Recovering a halted sequence | Retry the halted job, or retry a later job to skip it | Retry the halted job, or delete it. Retry always returns a sequence job to `pending` | A unique index allows one live job per sequence, so a retry can't jump the line or run beside the live job (River documents manual retries as able to break mutual exclusion). |
| Halting job retention | — | Exempt from the cleaner until retried or deleted | Otherwise a halted sequence would silently resume after the discarded retention. |
